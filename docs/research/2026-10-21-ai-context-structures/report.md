# Structure AI context by when it loads

Developers who get durable results from AI coding assistants don't organise context by folder. They organise it by **when it enters the model's context**, and every major tool now offers the same three tiers: an always-loaded root file, rules scoped to file paths, and material loaded on demand (skills, description-triggered rules, plain docs the agent reads when told to). A single `/docs` directory works fine as *storage* for the on-demand tier, but it isn't a context structure on its own. Claude Code never loads `/docs` automatically, and a prose line such as "Read PLAN.md first" is something the model may or may not act on. The controlled studies from 2026 point the same way: repository context files barely move task success, agents reliably follow the **specific, non-obvious instructions** in them, and architecture overviews don't help. So the better approach for this project is to split the 445-line `PLAN.md` by job. Section 0's working rules become a short always-loaded file. The volatile Progress checklist becomes a tiny status file that is imported deterministically. The Kubernetes/Terraform tutor rules and pitfalls become path-scoped rules. Multi-step procedures (teaching a module, closing a milestone) become skills. The app spec, curricula, ADRs and per-milestone notes live in `docs/` and are read on demand. Git history is the log. Heavy spec-driven frameworks (Spec Kit, BMAD, Kiro specs) are overkill for one person who is both PM and implementer, and doubly so in Parts 2–3, where a generated task list would be the solution you're meant to write yourself. For the portfolio, the strongest artefact is the context system itself, plus a visible record of what you reviewed and corrected.

## Every major tool now sorts context into three load tiers

Claude Code's own documentation sets the rules this design has to work within. CLAUDE.md files in the working directory and above it are **loaded in full at launch**. CLAUDE.md files in subdirectories load only once Claude reads or edits a file there. Everything that's discovered is concatenated, not overridden ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)). Two details matter most for this repo. First, `@path` imports are expanded at launch, so they "help you organize a long file but don't reduce its context cost" ([memory](https://code.claude.com/docs/en/memory)). Second, the only mechanisms that actually keep material out of context until it's needed are path-scoped `.claude/rules/*.md` files with `paths:` frontmatter, which load "when Claude uses the Read, Write, or Edit tool on a matching file", and Skills, whose body "loads only when it's used, so long reference material costs almost nothing until you need it" ([memory](https://code.claude.com/docs/en/memory); [skills](https://code.claude.com/docs/en/skills)). Anthropic's size guidance is to "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence" ([memory](https://code.claude.com/docs/en/memory)). It says to leave out "information that changes frequently" and "file-by-file descriptions of the codebase" ([best practices](https://code.claude.com/docs/en/best-practices)). It also says CLAUDE.md is "context, not enforced configuration": anything that must never happen belongs in hooks or permission settings ([memory](https://code.claude.com/docs/en/memory)).

Your current setup collides with one specific point in those docs. Your CLAUDE.md tells Claude in prose to read `PLAN.md`. Anthropic describes the equivalent AGENTS.md case this way: Claude "sees `AGENTS.md` only if it decides to open the file", and it recommends an `@` import instead ([memory](https://code.claude.com/docs/en/memory)). Importing all of `PLAN.md` would fix the reliability problem but load 445 lines of mostly irrelevant curriculum into every session. Splitting the file solves both.

The other tools have converged on the same shape under different names. **Cursor** has Always Apply, Apply Intelligently (only the description is present until relevant), Apply to Specific Files (globs) and Apply Manually, and it recommends rules "under 500 lines" ([Cursor Rules](https://cursor.com/docs/context/rules)). **Copilot** has an always-on `.github/copilot-instructions.md`, path-scoped `*.instructions.md` files with `applyTo` globs, and AGENTS.md, though support varies sharply by surface ([GitHub support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support)). **Kiro** has `.kiro/steering/` with `always`, `fileMatch`, `manual` and `auto` inclusion ([Kiro Steering](https://kiro.dev/docs/steering/)). **Windsurf/Devin Desktop** has `always_on`, `model_decision`, `glob` and `manual` triggers, capped at 12,000 characters per rule file ([Devin Desktop docs](https://docs.devin.ai/desktop/cascade/memories)). **Codex** concatenates AGENTS.md files from the git root down to the working directory and stops at a 32 KiB combined cap ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). Only the always-on tier is portable across tools, as **AGENTS.md**, which agents.md says is stewarded by the Agentic AI Foundation under the Linux Foundation ([agents.md](https://agents.md)). Since v2.1.277, Claude Code reads AGENTS.md natively, but by default only when no CLAUDE.md exists. Anthropic's documented multi-tool pattern is a CLAUDE.md that contains `@AGENTS.md` plus Claude-only notes. On Windows it explicitly advises against the symlink alternative, because Git can check a symlink out as a one-line text file ([memory](https://code.claude.com/docs/en/memory)).

| Mechanism | When it enters context | Best use in this repo | Verdict |
|---|---|---|---|
| Root `CLAUDE.md` / `AGENTS.md` | Every session, in full | Role split, environment, non-obvious rules, session rituals | Keep it short, under ~100 lines combined |
| `@import` | Every session, in full | A tiny status file that must always be present | Use for small files only; no token saving |
| `.claude/rules/*.md` with `paths:` | When a matching file is read or edited | Tutor mode and pitfalls for `k8s/`, `charts/`, `terraform/`; service conventions | Adopt |
| Nested `CLAUDE.md` | When a file in that folder is touched | Per-service commands, if they grow | Optional; rules cover it |
| Skills (`.claude/skills/`) | Description always; body when invoked | The 8-step teaching procedure; the milestone-close procedure | Adopt |
| Auto memory (`~/.claude/projects/.../MEMORY.md`) | First 200 lines / 25KB every session | Your preferences and feedback | Leave on; it's machine-local and invisible to portfolio readers |
| Plain `docs/*.md` | Only when the agent reads it | Spec, curricula, ADRs, milestone notes | Adopt as the on-demand tier |
| Permissions / hooks | Enforced by the harness | "Never `terraform apply` without my go-ahead" | Adopt for the money-spending and destructive commands |
| `llms.txt` | Never auto-loaded from a repo | Nothing | Skip |

`llms.txt` is worth a word because it keeps coming up. It is a website-root index of documentation links that agents use "on demand" ([llmstxt.org](https://llmstxt.org/)). None of the coding tools' documented file lists includes a repo-local `llms.txt`, so for this project it adds nothing.

## The evidence rewards short, specific rules over long overviews

The empirical picture is clearer than the hype. Gloaguen et al. tested Claude Code, Codex and Qwen Code on SWE-bench Lite and on a new benchmark built from repos with developer-written context files. They found that context files "do not generally improve task success rates, while increasing inference cost by over 20% on average" ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). Developer-written files gained about **+2.4%**, which is not significant, and LLM-generated files were slightly negative. The agents did follow specific instructions: a tool named in the file was used about **1.6 times per task, versus under 0.01** when it wasn't named. Codebase overviews did not help agents find the relevant files any faster ([arXiv HTML v3](https://arxiv.org/html/2602.11988v3)). Khatri's two-agent ablation saw the same flat pass rates. In it, an on-demand ("selective") strategy matched always-on loading and significantly cut Claude's cache-creation tokens, and a single specific warning ("tests are slow") cut wall-clock time by about 24% on one repo ([arXiv 2607.27250](https://arxiv.org/html/2607.27250v1)). Lulla et al. found AGENTS.md associated with **28.64% lower median runtime and 16.58% fewer output tokens** at comparable completion ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404)). Their result conflicts with Gloaguen's on cost, which reflects different agents and metrics.

Two further results bear directly on how you work. McMillan's factorial study of 1,650 Claude Code sessions found that file size, instruction position, single versus split files, and contradictions in adjacent files had no detectable effect on compliance. The largest effect came from **session length**: each additional generated function lowered the odds of compliance by about 5.6% ([arXiv 2605.10039](https://arxiv.org/abs/2605.10039)). The broader long-context research agrees. Chroma found degradation with input length across all 18 models tested, even on trivial tasks ([Chroma: Context Rot](https://www.trychroma.com/research/context-rot)). IFScale found that the best frontier models reach only 68% accuracy at 500 simultaneous instructions, with a bias toward earlier ones ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)). Anthropic's framing is to treat context as an "attention budget" and aim for "the smallest set of high-signal tokens", fetching everything else "just in time" ([Anthropic: context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Read honestly, these studies rule out large effects but not small ones. They're mostly Python, mostly bug-fix tasks, and none of them measured the instructions that matter most to you: "stop at the Done-when check", "teach, don't write the YAML", "tick only, never rewrite". So the case for a context system here doesn't rest on benchmark lift. It rests on process control across many sessions, which the benchmarks don't test. The design consequences still follow. Keep the always-loaded file to behavioural rules the model can't infer. Don't spend tokens describing the architecture the code already shows. Don't run `/init` to generate a file. Start fresh sessions between milestones instead of letting one session sprawl.

## Memory banks and spec frameworks: borrow the ideas, skip the machinery

The **Cline Memory Bank** is the best-known "context directory". It is six Markdown files: a stable `projectbrief.md`, `productContext.md`, `systemPatterns.md` and `techContext.md`, plus the volatile `activeContext.md` and `progress.md`. Its custom instruction reads "I MUST read ALL memory bank files at the start of EVERY task", and the command **"update memory bank"** forces a full review ([Cline Docs](https://docs.cline.bot/prompting/cline-memory-bank)). Roo Code forks add a `decisionLog.md` recording context, decision and rationale ([roo-code-memory-bank](https://github.com/GreatScottyMac/roo-code-memory-bank)). Three ideas survive: separate stable files from volatile ones, keep one small "current focus / next step" file that changes most often, and have one explicit sync command. The "read everything every task" rule doesn't survive. It was a workaround for tools that had no auto-loaded instruction file, and in Claude Code it just recreates the bloat problem. Practitioners report drift as the dominant failure ("documentation decays") ([PromptLayer](https://www.promptlayer.com/glossary/cline-memory-bank)), and Claude Code warns that when two instructions contradict each other, "Claude may pick one arbitrarily" ([memory](https://code.claude.com/docs/en/memory)).

Anthropic's long-running-agent harness adds the discipline a memory bank lacks: a **fixed session-start routine** (read the git log and progress file, pick the next item, run a smoke test before new work), a commit plus progress note at every session end, and a feature list whose only editable field is `passes`. JSON was chosen because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files" ([Anthropic: effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Anthropic's prompting guide likewise recommends structured formats for state, "unstructured text for progress notes", and git for tracking, and observes that Claude is "extremely effective at discovering state from the local filesystem" when it starts fresh ([Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Your milestones already have "Done when" checks, which are exactly the done-condition that keeps an agent from quietly redefining success, a failure Osmani names alongside premature completion and deleted tests ([Addy Osmani: long-running agents](https://addyosmani.com/blog/long-running-agents)). A Markdown checklist with an explicit **tick-only rule** is the human-scale equivalent of "only change `passes`".

Spec-driven frameworks fit this project less well. **GitHub Spec Kit** (1.0.0 in August 2026) runs constitution → specify → plan → tasks → implement → converge, with a numbered `specs/NNN-feature/` folder and branch per feature ([Spec Kit CHANGELOG](https://raw.githubusercontent.com/github/spec-kit/main/CHANGELOG.md); [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)). Its example constitution mandates Library-First and a CLI interface, defaults that would push a NestJS + Go web service in odd directions. **BMAD** has churned from v6.0 to v6.12 to a v7 preview in about a year. Its own guidance says a PRD is needed only "when more than one person must agree on what the product is" ([BMAD planning path](https://docs.bmad-method.org/plan/choose-a-planning-path/)). **Kiro** added "Quick Spec … without approval gates, for well-understood features" ([Kiro Specs](https://kiro.dev/docs/specs/)). **OpenSpec** is the lightest of the group. It keeps living specs plus per-change folders that are archived and merged on completion ([OpenSpec](https://github.com/Fission-AI/OpenSpec)). The most authoritative critique is Birgitta Böckeler's on martinfowler.com. She found the tools are mostly "spec-first", that Kiro turned a small bug into 4 user stories with 16 acceptance criteria ("a sledgehammer to crack a nut"), and she wrote: "I'd rather review code than all these markdown files" ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). Thoughtworks put SDD in "Assess", noting that "handcrafting detailed rules for AI ultimately doesn't scale" ([Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)). The vendors' own retreats from ceremony amount to agreement.

What's worth taking from SDD is small and cheap. Use `[NEEDS CLARIFICATION: …]` markers instead of guesses. Write acceptance lines in EARS form ("WHEN … THE SYSTEM SHALL …") ([Kiro Feature Specs](https://kiro.dev/docs/specs/feature-specs/)) so "Done when" items double as tests and quiz prompts. Treat the API contract (the OpenAPI document NestJS Swagger already produces) as the one spec that is also code. Most valuable of all are **ADRs**. They're short, numbered, superseded rather than edited, and MADR's "Considered Options" and "Pros and Cons" sections ([MADR](https://adr.github.io/madr/)) record *why*, which keeps the AI from re-litigating settled choices and gives you interview material. Because an ADR records a moment in time, it doesn't drift the way a description of current behaviour does. Diátaxis (tutorials, how-to, reference, explanation) is a sensible filing rule for whatever human-facing docs you add later ([diataxis.fr](https://diataxis.fr/)).

## A recommended layout: PLAN.md's four jobs become four tiers

Right now `PLAN.md` does four jobs: standing instructions (section 0), a stable spec (section 1), long curricula (sections 2–4), and volatile state (Progress). Each job belongs in a different tier. The tree below keeps your existing `docs/adr/` path and repo layout, and adds only what has a load-time reason to exist.

```text
product-catalog/
├── AGENTS.md                  # ALWAYS (via import). ~60–90 lines. From PLAN §0: about me, env (PowerShell/Win11/Docker),
│                              #   role split Part 1 vs Parts 2–3, rules, Part-1 pitfalls (OpenSearch, WSL memory),
│                              #   session start/close ritual, where things live (pointers, not copies)
├── CLAUDE.md                  # ALWAYS. ~10–20 lines: @AGENTS.md, @docs/STATUS.md, Claude-only notes
│                              #   (skills to use, "when compacting, preserve current milestone + next step")
├── PLAN.md                    # ON DEMAND. ~40-line roadmap index: Parts 1–4 goals, links to docs/plan/*
├── README.md                  # Human-facing; ends with "How this was built" (portfolio)
├── LEARNING-NOTES.md          # Yours alone, in your words. The AI reminds you; never edits it
├── .claude/
│   ├── settings.json          # ENFORCED. Deny/ask rules for terraform apply/destroy, kind delete cluster, etc.
│   ├── rules/
│   │   ├── tutor-mode.md      # paths: k8s/**, charts/**, terraform/**  → hints first, no solutions, review style
│   │   ├── k8s-pitfalls.md    # paths: k8s/**, charts/**  → ingress-nginx retired, Bitnami, kind image tags
│   │   ├── terraform-pitfalls.md # paths: terraform/**  → Helm provider v3 syntax, cost-safety reminders
│   │   └── services.md        # paths: services/**  → "Requirements for both services", test/run commands
│   └── skills/
│       ├── teach-module/SKILL.md     # The 8-step Parts 2–3 procedure (explain → task → hints → review → checks → quiz → notes → tick)
│       └── close-milestone/SKILL.md  # Run Done-when, update STATUS, write milestone note, propose commit
├── docs/
│   ├── STATUS.md              # ALWAYS (imported). ≤40 lines. "Now" block (rewritten) + tick-only checklist
│   ├── plan/
│   │   ├── app.md             # PLAN §1: architecture, data model, both services, Part 1 milestones + Done when
│   │   ├── kubernetes.md      # PLAN §2: K0–K8
│   │   ├── terraform.md       # PLAN §3: T0–T5
│   │   └── extras.md          # PLAN §4
│   ├── adr/
│   │   └── 0001-two-services-synchronous-indexing.md   # MADR-minimal; superseded, never edited
│   ├── milestones/            # One frozen note per finished milestone/module (the review record)
│   │   └── 2026-10-22-1.1-repo-scaffold.md
│   └── ai-workflow.md         # Human-facing explanation of this whole system (portfolio)
├── services/ … docker-compose.yml  k8s/  charts/  terraform/local/  terraform/aws/
```

`docs/STATUS.md` is the one volatile file that is always loaded. It stays deliberately tiny so the import costs almost nothing, and that import replaces the unreliable "read PLAN.md first". Its two sections have different edit rules, written at the top of the file:

```markdown
# Status  (AI rewrites "Now" each session; the checklist is tick-only)
## Now
- Current: 1.2 catalog-api. Redis cache done; e2e test next
- Last session: 2026-10-23 (commit abc1234)
- Next step: write the e2e test for POST /products
- Open questions / blockers: none
## Checklist  (change [ ] to [x], append date · commit · note link; never reword or delete items without asking)
- [x] 1.1 Repo scaffold · 2026-10-22 · a1b2c3d · docs/milestones/2026-10-22-1.1-repo-scaffold.md
- [ ] 1.2 catalog-api
```

Recording the commit hash next to each tick turns a progress claim into something you can check against git. A frozen milestone note per item lets the checklist stay one line per item forever. Path-scoped rules have one caveat. They load when Claude reads or edits a matching file, so at the very start of module K0, before any file in `k8s/` exists, they aren't present. That's why the one-line role split also stays in `AGENTS.md`, and why the `teach-module` skill carries the full procedure. It's also why the "never spend money" rule belongs in `settings.json` permissions rather than prose, because Anthropic is explicit that CLAUDE.md is advisory ([memory](https://code.claude.com/docs/en/memory)). If you use the superpowers `writing-plans` skill for a larger milestone, note that it saves to `docs/superpowers/plans/YYYY-MM-DD-<feature>.md` by default. User preference overrides that, so tell it to use `docs/milestones/` or let it keep its own folder ([superpowers writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)).

On AGENTS.md versus a single CLAUDE.md: since Claude Code is your only tool, a single CLAUDE.md would work. The `AGENTS.md` + `@AGENTS.md` split costs nothing (Anthropic confirms the import "never makes Claude read `AGENTS.md` twice"), it makes the repo legible to Codex, Cursor and Copilot, and for a portfolio it shows you know the cross-tool standard ([memory](https://code.claude.com/docs/en/memory)). Keep the Claude-specific parts (imports, skills, compaction note) in `CLAUDE.md`.

## A session workflow with fixed start and close rituals

The workflow follows from the tiers. Each session starts fresh from disk state, works on one milestone, and closes with a forced sync. McMillan's within-session decay result and Anthropic's harness both favour that over one long session that keeps getting compacted.

| Moment | What's in context | Who does what | Files touched |
|---|---|---|---|
| Launch | `AGENTS.md`, `CLAUDE.md`, `docs/STATUS.md`, auto-memory index, skill descriptions | Harness loads them; check with `/context` | none |
| Session start ritual (in `AGENTS.md`) | + `git log --oneline -10`, the current milestone's section of `docs/plan/*.md`, relevant ADRs | AI restates the current milestone and next step in 3 lines; runs a smoke check (`docker compose ps`, tests, or `kubectl get pods -n catalog`) before new work | none |
| Working, Part 1 | + `.claude/rules/services.md` once `services/**` is touched | AI writes code, flags `[NEEDS CLARIFICATION]` instead of guessing, proposes an ADR for any real decision | code, `docs/adr/` (new files only) |
| Working, Parts 2–3 | + `tutor-mode.md` and the pitfalls rule once your YAML/HCL is read; `teach-module` body when invoked | You write; AI explains, hints, reviews, quizzes | AI edits none of `k8s/`, `charts/`, `terraform/` unless you ask |
| Close (`/close-milestone`) | + `close-milestone` skill body | AI runs the Done-when checks with you, rewrites STATUS "Now", ticks the checklist, writes `docs/milestones/<date>-<id>.md` (what was built, decisions, your review findings and corrections; for Parts 2–3, quiz questions and where you struggled), proposes a commit with a co-author trailer | `docs/STATUS.md`, `docs/milestones/`, git |
| Between milestones | nothing | You run `/clear` and start a new session | none |
| End of each Part | `/doctor prompt-audit` output | AI proposes cuts to `AGENTS.md` and rules (anything the code shows, or that it does right unprompted); you approve | `AGENTS.md`, `.claude/rules/` |

Ownership is what stops drift, so every file gets one owner and one edit rule. You own `AGENTS.md`, the rules and `PLAN.md`. The AI may *propose* diffs to them but applies them only with your approval, and every new line should be "earned by a real failure" ([Addy Osmani](https://addyosmani.com/blog/long-running-agents)). The AI owns `STATUS.md` and the milestone notes, under the rewrite-"Now"/tick-only-checklist rule. ADRs are append-only: a changed decision gets a new ADR that supersedes the old one. `LEARNING-NOTES.md` is yours alone. Anthropic's test for any always-loaded line, "Would removing this cause Claude to make mistakes? If not, cut it" ([best practices](https://code.claude.com/docs/en/best-practices)), is the pruning criterion. The descriptive study of 2,303 real context files found they "evolve like configuration code through frequent, small additions" ([arXiv 2511.12884](https://arxiv.org/abs/2511.12884)), so without a scheduled prune the always-loaded tier will grow back to the size `PLAN.md` is now.

## Show the system, the reviews and the human-written half

The public examples readers find credible share three traits: a plain statement of the AI's role, inspectable artefacts, and visible human verification. Cloudflare's workers-oauth-provider says it was "largely written with the help of Claude", that "Claude's output was thoroughly reviewed by Cloudflare engineers", and invites readers to "check out the commit history to see how Claude was prompted" ([HISTORY.md](https://github.com/cloudflare/workers-oauth-provider/blob/main/HISTORY.md)). Simon Willison links his prompts and transcripts, and publishes what his review later found, including a login CSRF bug from an unchecked `state` parameter ([Willison, Nov 2024](https://feeds.simonwillison.net/2024/Nov/29/github-oauth-cloudflare/)). Harper Reed commits `spec.md`, `prompt_plan.md` and `todo.md` alongside the code ([harper.blog](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/)). Career-advice sources, which are opinion rather than surveys, agree that the red flag is unexplained AI output, not AI use ([Artech](https://www.artech.com/blog/ai-assisted-portfolio-credibility/)).

For this repo, the showcase is already most of the way there if the layout above is followed. The README's "How this was built" section states the split in two sentences: the AI wrote the Part 1 app under milestone-by-milestone review, and you wrote all the Kubernetes and Terraform with the AI as tutor and reviewer. `docs/ai-workflow.md` explains the load tiers, the ownership rules and the session ritual, so a reviewer can see you engineered the collaboration rather than just prompting. `docs/milestones/` is the evidence trail: each note records what you caught and made the AI change in Part 1, and what you got wrong and fixed in Parts 2–3. The ADRs show reasoning. Commits with co-author trailers, plus the tick-with-commit-hash checklist, make the timeline checkable. `LEARNING-NOTES.md` in your own words answers the "can you explain it?" question directly. Leave raw session transcripts out. No source recommends them, and curated artefacts carry the signal.

## Conclusion

The real question isn't `/docs` versus some other folder. It's which tokens the model sees in every session, which it sees only when it touches certain files, and which it fetches on demand. Answer that, and `/docs` becomes the right home for the on-demand tier rather than a dumping ground. The evidence also shifts what a context system is *for*. Benchmarks show it barely changes whether an agent can solve a coding task, so its value lies in **process control and continuity**: making the agent stop at review gates, stay in tutor mode, and leave a checkable trail. Those are the very properties a learning project needs and a portfolio reviewer wants to see.

Two implications are easy to miss. First, the tutoring half of the project is where structure matters most and where tool support is thinnest. Path-scoped rules, a teaching skill and a hard permission rule against costly commands together do what no single document can. Second, the context system is itself a portfolio piece. A small, pruned, deliberately tiered setup with a review record shows more LLM fluency than a large memory bank or a spec framework, because it shows you know what to leave out.
