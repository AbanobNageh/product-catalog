# 5.1 Stock filter and sort in search
- Date: 2026-10-25 · Commits: e6303b7, 1d8f3c8 · Plan: [2026-10-25-5.1-plan.md](2026-10-25-5.1-plan.md) · Spec: [agent-ready-api.md](../plan/agent-ready-api.md#51-stock-filter-and-sort-in-search)

## What was built
- **search-service** (`internal/query`):
  - `params.go`: `maxStock` goes through the same `intParam` helper as the price parameters: digits only, 0 to 2147483647, and blank means unset. The new `StockAsc` sort is accepted, and the sort error message lists it.
  - `build.go`:
    - `maxStock` becomes `{"range":{"stock":{"lte":N}}}` in `bool.filter`, so the facets count only the matching products.
    - `stock_asc` sorts by `stock` ascending, then by `id` like every other sort. It also applies when there's a text query `q`, so "low-stock phones" really come lowest first.
  - `stock` was already an `integer` in the mapping: no mapping change and no reindex.
- **catalog-api:**
  - `search.ports.ts`: `SearchSort` gains `'stock_asc'`, and `SearchQuery` gains `maxStock`.
  - `dto/search-products.query.ts`: `maxStock` uses the same decorators as `minPrice` (`toOptionalInt`, `@IsInt`, 0 to `INT4_MAX`), so a bad value gets catalog-api's own 400. `stock_asc` is added to `SORTS`.
  - Swagger, in the same change: the `maxStock` description, and the `sort` description says what `stock_asc` does (and that `relevance` without `q` falls back to `newest`).
  - Forwarding (`toSearchParams`) and the search cache key (`searchCacheKey`) already loop over every field, so they got tests and no code.
- **Tests.** Each new test was seen failing before the code that makes it pass. For the integration and e2e tests, that meant temporarily removing the feature code.
  - search-service:
    - Unit tests: parsing (values, blank and `%20`, `0`, and `-1`, `abc`, `2147483648`, `1.5` rejected) and the query body (filter, `lte: 0`, `stock_asc` with `q`).
    - Integration subtests against OpenSearch: `maxStock=2&sort=stock_asc` returns `[p2 p3 p4]` with matching facets, `maxStock=0` returns only the out-of-stock product, and `inStock=true&maxStock=2` applies both filters.
  - catalog-api:
    - DTO tests.
    - Forwarding: `maxStock=0` and `sort=stock_asc` are sent.
    - Cache key: unset, `5` and `0` give three different keys.
    - e2e: `maxStock=-1` and `abc` return the validator's exact messages, and a valid stock search reaches search-service with both parameters.
    - 174 unit tests (7 new).
- **Verified (Done-when), 2026-10-25, on the rebuilt Compose stack with 10,000 seeded products:**
  - `GET /products/search?maxStock=5&sort=stock_asc&size=100`: 1,255 hits, every one with stock ≤ 5 and in ascending order (page 1 is all 0, the last page is 5). The category, brand and price facets each add up to 1,255.
  - `maxStock=0`: 1,026 hits, all with stock 0. `inStock=true&maxStock=0`: 0 hits. `q=phone&maxStock=5&sort=stock_asc`: ascending by stock.
  - `maxStock=-1` and `maxStock=abc` return 400 from catalog-api's validator. `maxStock=` (blank) is ignored.
  - search-service: `go vet` and `gofmt` clean, and `go test -tags integration ./...` ok. catalog-api: `tsc`, 174 unit tests, e2e 2/2, lint (no new warnings) and build all pass.

## Decisions
- No ADR: the spec fixed the design.
- **`maxStock=0` is a real filter** ("out of stock only"), not "no filter". It's the classic falsy-zero bug, so it's tested at every layer: parsing, the query body, forwarding and the cache key.
- **Both services validate.** catalog-api is the public contract and answers with its own 400; search-service still protects itself.
- **Execution:** the user chose "Native" mode. The AI implemented all three tasks itself, then a fresh reviewer (a separate AI agent, read-only) checked the whole change. Its verdict: ready to merge, with no Critical or Important findings.
- **Rulings the AI made during the build** (from its ledger; the reviewer agreed with all of them):
  - The e2e 400 checks pin the exact validator messages. The plan only asked that the message "mention maxStock", which the old code already did ("property maxStock should not exist"), so that test could never fail.
  - The e2e test also checks what the fake search-service received, so forwarding is proven end to end.
  - Prettier's reflow of untouched lines was reverted (these files are formatted wider than Prettier's 80 columns), so the diff shows only the feature.
  - The commits waited for the user's yes at the close, instead of one commit per task.

## Review findings and corrections
- **The user tested the change and asked for no corrections.**
- **The fresh reviewer's three Minor findings**, and what the user decided:
  1. **A bad integer gets three error messages.** For example, `maxStock=-1` also gets "must not be greater than 2147483647", because `toOptionalInt` leaves non-digits as strings. `minPrice` and `maxPrice` already did the same. **The user moved it into 5.3** ([plan](../plan/agent-ready-api.md#53-api-keys-with-scopes), with a new Done-when line).
  2. **OpenAPI shows the integer query parameters as `number` with no bounds**, so an agent tool schema generated from `/docs-json` would allow `1.5` or `-1`. **Also moved into 5.3.**
  3. **The integration fixture has no two products with the same stock**, so `stock_asc`'s `id` tie-break is only unit-tested. Left as is.

## Follow-ups
- **5.3:** the two integer-parameter fixes above.
- **Search results can be up to 60 seconds stale.** If a write bumps the cache version before OpenSearch refreshes, the next search caches the old results for the 60 s TTL. This is the existing cache design, not new in 5.1, but a stock filter makes it more visible to an agent. 5.2 already plans the rule "read `GET /products/:id` before writing".
- **5.4:** an example search with `maxStock` in AGENTS.md "Commands", and the new parameter in the app.md endpoint table (user-owned).
