# 5.2 Optimistic concurrency (`If-Match`): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `PATCH` and `DELETE /products/:id` safe for an agent: a write conditioned on the version the client read fails with 412 instead of silently overwriting a newer write.

**Architecture:** A `version` integer column is incremented on every update and exposed as `version` in the product body and as a strong `ETag: "<version>"`. The controller parses an optional `If-Match` into an expected version. The service puts it in the write's `WHERE` clause (one query, no race), and on Prisma P2025 looks the row up to tell 404 from 412. Search hits get their own type without `version`.

**Tech Stack:** NestJS 12 on Express, Prisma 7.10.1 with PostgreSQL 18, Jest + supertest, Go 1.26.

**Spec:** [docs/plan/agent-ready-api.md](../plan/agent-ready-api.md), section "5.2 Optimistic concurrency (`If-Match`)". Design: [ADR-0019](../adr/0019-optimistic-concurrency-with-if-match.md) (Proposed; accepted at the close).

## Global Constraints
- **`If-Match` is optional.** Without it, `PATCH` and `DELETE` behave as today. Every update increments `version`, with or without it.
- **Accepted `If-Match`:** exactly one strong ETag, `"<n>"`, where n is a whole number from 1 to 2147483647. Surrounding whitespace is allowed. Anything else (`*`, `W/"3"`, `"3", "4"`, a bare `3`, `"abc"`, `"0"`) gets 400 with the message `If-Match must be one strong ETag such as "3", got <value>`.
- **Mismatch:** 412 with exactly this body shape: `{"statusCode":412,"message":"product changed: you sent version 3, current is 4","error":"Precondition Failed","currentVersion":4}`. A missing product is 404, also when `If-Match` was sent.
- **ETag:** `ETag: "<version>"` on `GET`, `POST` and `PATCH /products/:id`. Lists and search keep Express's own weak ETag.
- **Column:** `version INTEGER NOT NULL DEFAULT 1`, added by a new migration. Existing rows get 1.
- **Naming:** catalog-api's `SearchIndexer.remove(id, version)` becomes `remove(id, indexVersion)`. search-service's `?version=` parameter doesn't change.
- **Search:** `version` stays out of the search document and the search hit type.
- **Swagger:** document the `If-Match` header, the 412, the `ETag` header and the retry rule in the same change (`.claude/rules/services.md`). No new libraries.
- **Versions and docs stay as they are:** the version bump, the `app.md` endpoint tables and the AGENTS.md examples are 5.4.
- **Commits** only with the user's yes, so they are proposed at the close. Suggested messages are given per task.

## Review Focus
1. **A product cached in Redis before this release has no `version`.** For up to 5 minutes after the upgrade, `GET` would send `ETag: "undefined"`. A cached entry without a numeric `version` must count as a miss. Test in Task 2.
2. **Express's weak body-hash ETag sent back in `If-Match`** (an agent copying the header from a list or search response, or from the previous release) must get a 400 naming the expected format, never a 412 or a 500. Test in Task 4 (unit and e2e).
3. **`If-Match` on a product that doesn't exist** (deleted, or a random UUID) must be 404, not 412. Test in Task 3 (unit) and Task 4 (e2e).
4. **A rejected write must not use up a version.** An empty body (400) and a duplicate sku (409) sent with a correct `If-Match` leave `version` unchanged, so the client's ETag stays valid. Test in Task 3 (empty body never reaches Prisma) and Task 4 (e2e: a 409 with `If-Match`, then the same ETag still works).
5. **A stale `DELETE`** must be refused (412) and leave the product, its cache entry and the search index untouched (no `indexer.remove`, no version bump). Test in Task 3.

### Task 4: `If-Match` and `ETag` over HTTP

**Files:**
- Create: `services/catalog-api/src/products/if-match.ts`
- Test: `services/catalog-api/src/products/if-match.spec.ts`
- Modify: `services/catalog-api/src/products/products.controller.ts`
- Test: `services/catalog-api/src/products/openapi.spec.ts`, `services/catalog-api/test/products.e2e-spec.ts`

**Interfaces:**
- Consumes: `ProductsService.update(id, dto, expectedVersion?)` and `remove(id, expectedVersion?)` (Task 3), and `ProductResponse.version` (Task 2).
- Produces:
  - `parseIfMatch(header: string | undefined): number | undefined`: `undefined` for a missing or blank header, the version for a valid one, and `BadRequestException` with the Global Constraints message otherwise.
  - `etag(version: number): string`, which returns `"<version>"` with the quotes.

- [ ] **Step 1: Write the failing tests**
  - `if-match.spec.ts`:
    - `parseIfMatch`: `undefined` → `undefined`; `''` and `'  '` → `undefined`; `'"3"'` → 3; `' "3" '` → 3; `'"2147483647"'` → 2147483647.
    - It rejects with a `BadRequestException` whose message contains `If-Match must be one strong ETag such as "3"`: `'*'`, `'W/"3"'`, `'"3", "4"'`, `'3'`, `'"abc"'`, `'"0"'`, `'"2147483648"'`, `'"-1"'`, and Express's weak hash `'W/"124-rj280D5nqySaOzAwMZHN6LZE1Qw"'` (Review Focus 2).
    - `etag(4)` → `'"4"'`.
  - `openapi.spec.ts`:
    - `PATCH /products/{id}` and `DELETE /products/{id}` document `412` and an optional `If-Match` header parameter.
    - `GET`, `POST` and `PATCH` document an `ETag` response header.
    - The PATCH 412 description mentions the retry rule (contains `re-read`).
    - The `GET /products/search` 200 description contains `GET /products/:id before writing`.
  - `products.e2e-spec.ts`, a new `it('refuses a stale If-Match with 412 and keeps ETag equal to version')`. Set `fake.status = 200` first: the lifecycle test leaves it at 503. Use a fresh product with a unique sku:
    1. `POST` → 201, `version: 1`, and the `etag` header is `"1"`.
    2. `GET` → the `etag` header is `"1"`, and the body's `version` is 1, so the product is now cached.
    3. `PATCH` with `If-Match: "1"` and `{ stock: 2 }` → 200, `version: 2`, `etag` `"2"`.
    4. The same `PATCH` again with `If-Match: "1"` → 412, and the body equals the Global Constraints object with `you sent version 1, current is 2` and `currentVersion: 2`.
    5. `GET` → `stock` 2 and `version` 2: the 412 changed nothing, and the cache was invalidated by step 3.
    6. `PATCH` without `If-Match` → 200, `version: 3` (the condition stays optional).
    7. `PATCH` with `If-Match: W/"1"` → 400, and the message contains `If-Match must be one strong ETag`.
    8. Review Focus 4: create a second product B, then `PATCH` with `If-Match: "3"` and B's sku → 409. Then `PATCH` with `If-Match: "3"` and a valid body → 200, `version: 4`.
    9. `GET` with `If-None-Match: "4"` → 304.
    10. `DELETE` with `If-Match: "1"` → 412, then `GET` → 200.
    11. `DELETE` with `If-Match: "4"` → 204, then `DELETE` with `If-Match: "4"` → 404.
    12. `PATCH /products/<random UUID>` with `If-Match: "1"` → 404.
- [ ] **Step 2: Run them and see them fail**
  Run: `npm test`, then `docker compose up -d postgres redis` and `npm run test:e2e`
  Expected: FAIL. `if-match.ts` doesn't exist yet, the OpenAPI document has no 412 or `If-Match`, and in the e2e test no `ETag` equals `"1"` (Express sends a weak hash).
- [ ] **Step 3: Implement**
  - `if-match.ts` with the Produces block.
  - Controller:
    - `findOne`, `create` and `update` take `@Res({ passthrough: true }) res: Response` (from `express`) and call `res.setHeader('ETag', etag(product.version))`. Express then keeps our header instead of generating its own, and it answers `If-None-Match` from it.
    - `update` and `remove` take `@Headers('if-match') ifMatch?: string` and pass `parseIfMatch(ifMatch)` to the service.
  - Swagger:
    - `@ApiHeader({ name: 'If-Match', required: false, description: 'Optional. The ETag from GET /products/:id, for example "3". A stale version gets 412' })` on PATCH and DELETE.
    - `@ApiPreconditionFailedResponse` on both. For PATCH, the description says: "The product changed since you read it; the body has currentVersion. If you are retrying after a timeout, re-read the product: your first attempt may have succeeded".
    - An `ETag` entry in the `headers` of the GET/POST/PATCH success responses.
    - The 400 descriptions also mention a malformed `If-Match`.
    - The `GET /products/search` 200 description adds: "Hits have no version and may be stale: read GET /products/:id before writing".
