# 1.3 search-service
- Date: 2026-10-22 · Commits: 99ca6da · Plan: [2026-10-22-1.3-plan.md](2026-10-22-1.3-plan.md)

## What was built
`services/search-service`, a Go 1.26 service (stdlib `net/http` and `log/slog`, plus `opensearch-go` v5.1.1 as the only dependency), and OpenSearch 3.9.0 in `docker-compose.yml`.
- **Index:**
  - `products-v1` behind the alias `products`, created together in one atomic call at startup ("already exists" counts as success, for replicas racing).
  - The mapping is explicit and `dynamic: strict`.
  - Every read and write goes through the alias.
- **Endpoints:**
  - `PUT /products/{id}` returns `{"result":"indexed"|"skipped"}`.
  - `DELETE /products/{id}` returns 204 and is idempotent.
  - `POST /products/_bulk` returns 200 with `{indexed, skipped, failed:[{id,status,reason}]}`.
  - `GET /search` supports `multi_match` on `name^3`/`description` with fuzziness, filters, four sorts with an `id` tie-break, and category, brand and price facets. The JSON matches catalog-api's `SearchResult` field for field.
  - `/healthz` and `/readyz` (alias exists).
- **Write safety:**
  - Writes are versioned by `updatedAt` in ms (`external_gte`), so a stale write is skipped.
  - Single writes use `refresh=wait_for`.
  - Writes use `require_alias`, and deletes go through `_bulk`, so a missing alias is never replaced by an auto-created index.
- **Operability:**
  - env-only config that reports every bad value at once
  - JSON logs, with one line per request
  - a 2s deadline on every OpenSearch call (10s for bulk)
  - a 30s bounded startup wait, then exit 1
  - SIGTERM drains within 9s
- **Image:** two stages to `gcr.io/distroless/static-debian13:nonroot`, 19 MB.
- **Tests:**
  - table-driven unit tests for config, product validation, error classification, the query builder, response parsing and the handlers (against fakes)
  - integration tests behind the `integration` tag, against the Compose OpenSearch, on throwaway `it-*` indexes
  - 65 top-level tests in all
- **Verified live:**
  - the Done-when curl: bulk-loading 30 sample products, then a filtered search with facets
  - OpenSearch stopped: search, readiness, PUT and DELETE all return 503 in about 40ms
  - OpenSearch paused: 503 in about 2.04s
  - recovery once OpenSearch is back
  - the image on the Compose network: `docker stop` exits 0 in 0.4s, running as `nonroot`
  - startup with no OpenSearch: exit 1 after 30s, with the URL in the log

## Decisions
- [ADR-0005](../adr/0005-opensearch-go-v5.md), accepted at this close:
  - **opensearch-go v5 instead of the spec's v4:** v5 is tested against OpenSearch 3.x, and it reports partial bulk failures by default.
  - **Client config:** discovery and built-in retries are off. The default router stays on, but with discovery off it only knows the seed URL.
  - **OpenSearch pinned to `3.9.0`,** because `latest` points at the 2.19 line.
  - **Go stays on 1.26.**
- **Spec answers from the user**, added to `docs/plan/app.md`:
  - Facets count only the filtered results.
  - The price buckets are fine and can change later (they're one constant).
  - The bulk response is **200 with a per-item report**, not 500.
  - The module path is `github.com/AbanobNageh/product-catalog/services/search-service`.
- **`external_gte`, not `external`:** equal versions overwrite, so reindexing unchanged data isn't all "skipped", and a second update within the same millisecond isn't lost.
- **No `action.auto_create_index=false` in Compose:** the code protects itself, and the cluster setting would have made the integration test that proves it pass even if the code were wrong.
- **A missing alias during bulk is a 503 for the whole call,** not 200 with every item failed. It's a service fault, not a product fault.
- **A client disconnect writes nothing** and is logged at debug.

## Review findings and corrections
**From the user:**
1. **Bulk with failures:** "if I saw 500, I would assume the server itself had an issue." The AI had proposed 500 with the failed ids. It checked the conventions (OpenSearch's own `_bulk`, 207 Multi-Status), agreed, and changed the design to 200 + `indexed/skipped/failed`. 400 is for a malformed body and 503 for OpenSearch unavailable.
2. **"What are the questions?"** The user asked to see the full list of open questions instead of the one-at-a-time interview, then answered the four that only they could, and accepted the defaults for the rest.
3. **The Done-when curl failed** with "error encountered when reading a file". The `@testdata/...` path is relative, and the instructions had said which directory to use only in prose. The AGENTS.md command now starts with `Set-Location`.

**From a fresh-context AI review of the plan, before any code.** It checked the plan against the downloaded v5 source. All were fixed in the plan:
1. v5 retries up to 6 times by default, which broke "no retries" → `DisableRetry: true`.
2. v5 errors often carry no typed status (HEAD calls, non-JSON bodies). As written, `Ready` could never have reported "alias missing", and a 503 during boot would have looked permanent. → The status is read from the response.
3. A delete against a missing index would have returned 204. → A missing *document* and a missing *index* are now told apart.
4. OpenSearch validates a whole bulk request first, so one long id or a pre-1970 `updatedAt` would reject the batch. → Both are validated before sending.
5. Smaller fixes: `*int` vs `int64` for `Version`, two JSON tags, and HTML escaping (`&` would have become `&`).

**Found by the AI's own live checks:**
- **With OpenSearch stopped, `/search` returned 500.** Docker's port forward accepts the connection and then closes it, so the client gets `EOF`, which isn't a network error. `Classify` now treats `EOF` and `ErrUnexpectedEOF` as unavailable (test-first).

**From the fresh-context AI review of the finished change.** It found nothing critical. Fixed test-first:
1. **Important: a missing `priceCents`/`stock` was indexed as 0** (free, out of stock, first in `price_asc`), and one wrongly typed field rejected the whole bulk. → `catalog.DecodeProduct` and per-item decoding, so each bad product lands in `failed` with its id.
2. **A very long `q` returned 500** (OpenSearch `too_many_clauses` at about 1,500 words). The AI re-graded it from Minor to Important because any user can trigger it. → `q` is capped at 200 characters, with a 400.

## Follow-ups
- **1.4 (catalog-api ↔ search-service):**
  - The HTTP `SearchIndexer.bulkUpsert` must read `failed` and pass those ids back from `/admin/reindex`, instead of turning any failure into 503.
  - The search DTO should also reject `page × size > 10000`, `minPrice > maxPrice` and a `q` over 200 characters, so users get catalog-api's own 400.
  - Use a 2s timeout on single calls, and at least 10s on the reindex bulk call.
  - Add search-service to Compose: depends on OpenSearch being `healthy`, `OPENSEARCH_URL=http://opensearch:9200`.
- **K3/K4:**
  - `/readyz` can take up to 2s, longer than Kubernetes' default 1s probe timeout.
  - Startup exits 1 after 30s without OpenSearch, so expect restarts until it's ready, or use a startupProbe.
- **Deferred minors:**
  - If `products-v1` is deleted while the service runs, it returns 503 until restarted (`Ensure` runs only at startup). Fix by hand: restart search-service, then reindex.
  - SIGTERM during the 30s startup wait exits 1 instead of 0.
  - Trailing data after a JSON body is accepted (`{"products":[]}garbage` → 200).
- **Known limits (accepted):**
  - Deletes aren't versioned, so a stale upsert arriving after a delete brings the product back (ADR-0001; Part 4's outbox fixes it).
  - OpenSearch logs harmless performance-analyzer `ERROR` lines at startup.
