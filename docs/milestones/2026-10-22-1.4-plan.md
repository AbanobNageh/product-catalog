# 1.4 Wire up + Compose Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** catalog-api calls the real search-service over HTTP, the whole stack runs with `docker compose up --build`, and `npm run seed` loads 10,000 products and reindexes them.

**Architecture:**
- catalog-api's two search ports (`SearchIndexer`, `SearchClient`) get HTTP adapters built on one helper, `callSearchService`. That helper owns timeouts and error mapping, using Node's built-in `fetch`. The 1.2 stubs are deleted.
- Compose adds a one-shot `migrate` service, `search-service` and `catalog-api`, with healthchecks and `depends_on` conditions. search-service gets a `healthcheck` subcommand, because distroless has no shell or curl.
- The seed lives in catalog-api's source and image (ADR-0006). It writes to Postgres directly, then calls `POST /admin/reindex`.

**Tech Stack:**
- catalog-api: Node 24 global `fetch` + `AbortSignal.timeout` (no axios, no `@nestjs/axios`), and `@faker-js/faker` **10.6.0**, exact pin, as a production dependency. It is ESM-only like Nest 12, so ADR-0004's setup covers it.
- search-service: standard library only, no new dependencies.
- Compose images: the existing pins, plus `opensearchproject/opensearch-dashboards:3.9.0` (the tag exists; checked 2026-10-22).

**Spec:** [`docs/plan/app.md`](../plan/app.md): catalog-api, Requirements for both services, milestone 1.4. Contracts:
- search-service's HTTP API: [`internal/httpapi/handlers.go`](../../services/search-service/internal/httpapi/handlers.go)
- the bulk result: [`internal/indexer/indexer.go`](../../services/search-service/internal/indexer/indexer.go) `BulkResult`
- the search params: [`internal/query/params.go`](../../services/search-service/internal/query/params.go)

Follow-ups carried in: [1.3 note](2026-10-22-1.3-search-service.md#follow-ups), [1.2 note](2026-10-21-1.2-catalog-api.md#follow-ups).

## Global Constraints
- **Timeouts:**
  - search, upsert and remove: **2000 ms**
  - bulk: **15000 ms**. That's at least search-service's own 10s bulk deadline, so search-service answers with its own 503 before we give up.

  The timeout covers reading the body too. **No retries anywhere.**
- **Error mapping (catalog-api → search-service):**
  - network error, DNS failure, timeout or any **5xx** → `SearchUnavailableError`
  - any other non-2xx → `SearchServiceError(status, message)`. That's a contract bug between our two services. It surfaces as **500** (search, reindex) or is logged (writes), never as 503.
  - a 2xx with an unparsable body → let the `SyntaxError` propagate (500).
- **`SEARCH_SERVICE_URL` is now required:** an `http(s)` URL with a host, with any trailing `/` removed. A bad value joins the existing "every problem at once" config error.
- **catalog-api `/readyz` stays Postgres + Redis only.** search-service being down must not take catalog-api out of rotation (ADR-0001).
- **Exact version pins** (repo convention). Compose images are never `latest`.
- **Commands:** every new run, test or seed command goes into `AGENTS.md` **Commands** (PowerShell) in the same task.
- **Never** run `docker compose down -v` or delete volumes without asking first.

## Review Focus
1. **search-service stopped or killed mid-request.** In Compose the DNS name disappears. On a Windows host, a refused connection to localhost can take about 2s. Expected: search returns 503 within ~2s, and writes still return 2xx with the error logged. → Task 2 (closed port, hang, body stalls) + Task 3 e2e (fake switched to 503) + Task 8.
2. **Falsy and special query values:** `minPrice=0`, `inStock=false`, and `q` containing `&`, `#`, `+` or non-ASCII text. Expected: search-service receives exactly those values. `0` and `false` must not be dropped as falsy. → `toSearchParams` test (Task 3).
3. **A reindex where some items fail** (search-service returns 200 with a non-empty `failed`). Expected: 200, with `failed` listing every id across all batches. Not a 503, not silently dropped. → Task 4.
4. **A reindex failing for a non-search reason** (Postgres down). Expected: the real error (500, logged), not "search is unavailable". The search version is still bumped. → Task 4.
5. **Running the seed twice.** Expected: still 10,000 seed rows (deterministic SKUs plus `skipDuplicates`), and the reindex runs again. → Task 6 generator test + Task 8 check.

## Resolved questions (user, 2026-10-22)
- **Seed ships in the runtime image** (ADR-0006, Proposed). K2 can run it as a Job or with `kubectl exec`.
- **search-service healthcheck:** a `healthcheck` subcommand of the binary. The image stays distroless.
- **Migrations in Compose:** a one-shot `migrate` service built from the Dockerfile's existing `build` stage. No new Dockerfile stage, so K3's migration-image decision stays open.

**AI defaults (say if you disagree):**
- **e2e tests use an in-process fake search-service**, not the real one. A real one would write `catalog_test` products into the dev `products-v1` index during reindex.
- **search-service publishes no port in Compose.** It's internal only, which previews a ClusterIP Service, and a native `go run` on 8080 doesn't clash with it.
- **Dashboards** sit behind the Compose profile `dashboards`, so they don't start by default (they use about 1 GB of RAM).
