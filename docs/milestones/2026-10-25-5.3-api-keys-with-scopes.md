# 5.3 API keys with scopes
- Date: 2026-10-25 · Commits: f1bc8c8, 4176754 · Plan: [2026-10-25-5.3-plan.md](2026-10-25-5.3-plan.md) · Design: [ADR-0020](../adr/0020-api-keys-with-scopes.md)

## What was built
- **catalog-api, keys and scopes:**
  - **`src/auth/`:**
    - `scope.ts`: the three scopes, `read` < `write` < `admin`.
    - `auth.decorators.ts`: `@RequireScope`, which also adds the Swagger security entry and the 401/403 responses, and `@Public()`.
    - `api-key.guard.ts`: the global guard (`APP_GUARD`). It reads `Authorization: Bearer <key>` and compares the key's SHA-256 digest with all three keys using `timingSafeEqual`. A route without a decorator is refused.
    - `routes.spec.ts`: walks every controller in the app's module graph and checks the exact route-to-scope map.
  - **Errors:** 401 with `WWW-Authenticate: Bearer`, or 403 such as `this endpoint needs the admin scope; your key has write`. Logs carry the scope, never the key.
  - **Config:** `READ_API_KEY`, `WRITE_API_KEY` and `ADMIN_API_KEY` are required. `src/config/api-key-format.ts` requires visible ASCII and at least 32 characters, and the keys must all differ.
  - **Swagger:** the bearer scheme (`bearerFormat: "API key"`), so the **Authorize** button works in `/docs`.
- **Integer query parameters (the 5.1 review):** `src/common/int-query-param.ts` gives each bad value one message, `<name> must be a whole number from <min> to <max>`. OpenAPI shows each parameter as `integer` with bounds. Used on search's `minPrice`, `maxPrice`, `maxStock`, `page` and `size`, and on the list's `page` and `limit`.
- **Every client sends a key:**
  - **The seed:** `CATALOG_API_KEY` (the admin key). `src/seed/reindex-call.ts` checks it before inserting anything, and explains a 401 or 403.
  - **k6:** `API_KEY` is required.
  - **e2e:** `test/auth.e2e-spec.ts` covers every scope on every endpoint group.
  - **Dev keys** marked "not secret" in Compose, `.env.example` and `.env.test.example`. The user's local `.env` got them too.
  - **AGENTS.md "Commands":** the keys, the rotation command, and the PowerShell quoting rule.
- **Release 0.2.0.** The user moved the bump here from 5.4, because `kind_load` only loads an image whose tag changed. catalog-api and search-service are `0.2.0`, and the chart is `0.3.0`.
- **Chart:**
  - catalog-api and the seed hook read the keys from the Secret `catalog-api-keys` (`catalogApi.apiKeysSecret`). The chart doesn't create it.
  - `validate.yaml` refuses an empty Secret name.
  - A `checksum/api-keys` pod annotation means rotating a key restarts the pods.
- **Terraform `modules/app`:**
  - `random_password` for each scope.
  - `kubernetes_secret_v1` created before the release.
  - A hash of the keys passed to the release.
  - Sensitive outputs `read_api_key`, `write_api_key` and `admin_api_key`.
  - The roots pin `hashicorp/random ~> 3.9` (3.9.1).
- **AWS:** `terraform/aws/app` gets the same Secret, and was checked with `validate`, `tflint` and `trivy` (its plan needs the cluster). The T5 runbook now uses the `0.2.0` image tags and a keyed smoke test.

## Decisions
- [ADR-0020](../adr/0020-api-keys-with-scopes.md), accepted at this close: static keys, three nested scopes, one environment variable per scope, closed by default.
- **The user's choices:**
  - Move the version bump from 5.4 into 5.3, and build dev at 0.1.1 first so the upgrade path is tested (the Part 5 plan was updated).
  - "Native" execution.
  - Move the 5.1 review's integer-parameter fixes into 5.3.
- **The design:** the keys never pass through Helm values (which end up in the release history). Terraform owns the Secret, and the chart only knows its name.
- **Rulings the AI made during the build** (27 in its ledger; the notable ones):
  - A blank `page`, `size` or `limit` now means the default (it was a 400), matching "blank means unset" for the other parameters.
  - `search-service:0.1.0` was rebuilt from the `v1.0.0` tag, because Compose had re-tagged newer code as `0.1.0`. That made dev's "before" install the real old release.
  - The rotation fix passes a hash of the keys rather than the Secret's `resource_version`. A server-computed value can show its old value at plan time, but a replaced key makes the hash unknown, which forces the upgrade.
  - The seed's env check and reindex call moved to `reindex-call.ts`, so they can be unit-tested.

## Review findings and corrections
- **The fresh reviewer** (a separate AI agent, read-only) said "with fixes". It probed the live API and found:
  - no open endpoint (including HEAD, different letter case and trailing slashes);
  - no 500 on a malformed header;
  - no key leak in the normal paths.
- **Fixed test-first in one pass:**
  1. **Rotating a key didn't restart the pods** (Important). Running pods kept accepting the old key, and staging's autoscaled pods would have mixed old and new keys. Fix: the `checksum/api-keys` annotation from a hash of the keys. The rotation command's PowerShell 5.1 quoting was also broken; it was fixed and tested with a real plan.
  2. **Keys with whitespace or non-ASCII characters were accepted** (Minor, re-graded Important). The app started, then refused every request, and undici's error message could have put such a key into the seed's log. Fix: one shared format check in the app and the seed.
  3. **OpenAPI said the keys were JWTs** (Minor, re-graded Important: agent tooling reads the document). Fix: `bearerFormat: "API key"`.
- **The user** ran every apply and the k6 test, reviewed the result, and asked for no corrections. The user approved the close, which accepted ADR-0020.
